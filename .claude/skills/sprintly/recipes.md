# sprintly recipes

Concrete flows you can paste with minor tweaks. All assume `sprintly` from PATH (or `~/.sprintly/bin/sprintly`).

Reference IDs used below come from `sprintly projects` / `statuses` / `types` / `sprints` and will differ between environments. Discover them once per session and reuse.

> **Formatting reminder.** Body of `--description` and `--notes` is rendered as HTML by the web UI. Always wrap content in primitive tags (`<p>`, `<h2>`, `<ul><li>…</li></ul>`, `<code>`, `<pre>`, `<b>`, `<i>`, `<br>`). Markdown (`**bold**`, `# heading`, backticks, `- list`) renders as raw syntax — do not use it. Plain unwrapped text is acceptable for one-line notes but `<p>…</p>` is preferred.

## 1. Create a task in the current sprint, assigned to me

`me` resolves to the signed-in user on `issue create` and `issue update` too — no need to look up the numeric ID first.

```bash
sprintly issue create \
  --project 8 --type 1 --sprint 8 --assignee me \
  --priority 4 --subject "Investigate flaky build" \
  --description "<p>Reproduce locally, isolate the failing step, file a follow-up if the fix is non-trivial.</p>"
```

## 2. Move issue N to In Progress

`in progress` status ID comes from `sprintly statuses`. In a fresh sprintly env it is typically `2`, but verify.

```bash
sprintly issue update --id N --status 2 --notes "<p>Picking this up.</p>"
```

## 3. List my open issues across all projects

```bash
sprintly issue list --assignee me --status open --all \
  --sort priority:desc,updated_on:desc \
  --columns id,project,type,status,priority,subject
```

## 4. Move issue to Review with a journal comment

```bash
# Discover the status ID once
sprintly statuses
# Then transition with a short HTML summary
sprintly issue update --id 39 --status 6 --notes \
  "<p>Done, please review.</p><ul><li>Skill files under <code>.claude/skills/sprintly/</code></li><li>Smoke test green</li></ul>"
# Verify the note landed by reading the issue's comments back
sprintly issue show 39 --comments
```

## 5. Batch-create from JSON

`--json-stdin` reads exactly one JSON object. Loop in your shell for batches.

```bash
while IFS= read -r line; do
  echo "$line" | sprintly issue create --json-stdin \
    --project 8 --type 1 --sprint 8 --assignee 9 --priority 4
done <<'EOF'
{"subject":"Add /healthz endpoint","description":"<p>Lightweight liveness probe; no DB hit.</p>"}
{"subject":"Cover login flow with tests","description":"<p>Happy path only for now.</p>"}
EOF
```

The `description` field in each JSON object follows the same HTML rule as `--description` / `--notes`.

CLI flags override JSON keys, so constants (project/type/sprint/assignee/priority) stay outside the JSON.

## 6. Inspect custom fields, then filter / set them

Without administrator rights the full dictionary is unavailable. The command
does not fail: it says so on stderr and falls back to the fields it can see on
issues, so `POSSIBLE VALUES` lists **values already in use**, not the allowed
set, and `FORMAT`/`REQ` come back empty. Narrow it with `--project` to keep the
sample relevant.

```bash
# Discover IDs and value sets
sprintly custom-fields --project 8 --type 1

# Filter issues by a custom field
sprintly issue list --project 8 --cf 66=2026.07.0 \
  --columns id,subject,cf:66

# Set a custom field on update
sprintly issue update --id 39 --cf 66=2026.07.0
```

## 7. Smoke test (matches #39 acceptance criterion)

End-to-end create → update → list, in one session.

Two things bite here, both verified on a live tracker:

- **A project may have required custom fields.** On `spr`, `Release Version`
  (CF 67) is mandatory, and omitting it fails the create with
  `HTTP 422: {"errors":["Release version cannot be blank"]}`. Check with
  `custom-fields --project <ID>` before assuming the minimal call works.
- **Assign to yourself if you then filter by `--assignee me`.** Creating the
  issue for someone else and listing it under `me` returns nothing, and that
  looks like a broken list rather than a correct one.

```bash
# Create — read the id straight out of --json (flat object, no envelope)
NEW_ID=$(sprintly issue create \
  --project 4 --type 1 --sprint 8 --assignee me --priority 4 \
  --cf 67=111 \
  --subject "Skill smoke test" \
  --description "<p>Generated by the sprintly skill smoke test.</p>" \
  --json | jq -r .id)

# Transition + comment
sprintly issue update --id "$NEW_ID" --status 2 --notes "<p>Transitioning via skill.</p>"

# Verify it shows up under "me / open"
sprintly issue list --assignee me --status open --subject "Skill smoke test" \
  --columns id,status,subject

# Close it — there is no delete, so a closed issue is the clean end state
sprintly issue update --id "$NEW_ID" --status 3 --notes "<p>Smoke test complete.</p>"
```

If every command succeeds and the listing reflects the transition, the skill is sufficient for an LLM to drive without extra hand-holding.

## 8. Find a numeric user id by name

Useful when `me` does not apply (e.g. setting `--watcher` on an issue, or assigning to someone else).

```bash
sprintly users --name larson --columns id,login,name,email
```

Plain `users` needs admin rights and answers `403` otherwise. Use project
memberships instead — open to any member of the project:

```bash
sprintly users --project 4 --name larson
```

For `--assignee` the lookup is not needed at all: `issue create` and
`issue update` resolve a name against the project members themselves.

```bash
sprintly issue update --id 39 --assignee larson
```

Matching is exact-case-insensitive first, then substring; zero or several
matches fail with the member list printed, so it never guesses. Note that
`issue list --assignee` still takes `ID` or `me` only.

`--watcher` remains numeric, so plug the id in there:

```bash
sprintly issue update --id 39 --watcher 9
```

## 9. List visible wiki pages of a project

```bash
# By slug
sprintly wiki list --project spr

# Walk a long index with client-side pagination
sprintly wiki list --project spr --limit 50 --offset 50
```

## 10. Read a wiki page, optionally pinned to a version

```bash
# Current revision
sprintly wiki show --project spr --title "Release notes"

# A specific historical revision, with attachments table
sprintly wiki show --project spr --title "Release notes" \
  --version 3 --with-attachments
```

## 11. Upsert a wiki page (create or update by title)

`wiki edit` is a single command for both create and update — the backend keys pages by title. Body source is exactly one of `--text` / `--text-file` / `--text-stdin`.

```bash
# Inline
sprintly wiki edit --project spr --title "Release notes" \
  --text "<p>2026-07-01: shipped #54.</p>" \
  --comments "ship note for sprint 1"

# From a file, set a parent page
sprintly wiki edit --project spr --title "Auth runbook" \
  --text-file ./auth-runbook.html --parent "Runbooks"

# From a pipeline (e.g. generator output)
some-generator | sprintly wiki edit --project spr \
  --title "Daily report" --text-stdin
```

Body follows the same primitive-HTML rule as issue descriptions / notes — Markdown is not interpreted.

## 12. Bulk-edit the descriptions of every sub-task of a story

The read-modify-write loop. `--json` gives the IDs, `--field description --raw` gives the body with nothing to strip, `--description` writes it back. No direct REST calls needed.

```bash
PARENT=161

# 1. Every sub-task id, machine-readable (--all so nothing is left on page 2)
ids=$(sprintly issue list --parent "$PARENT" --status '*' --all --json | jq -r '.[].id')

# 2. Read, transform, write back — one issue at a time
for id in $ids; do
  body=$(sprintly issue show "$id" --field description --raw \
           | sed -e 's|<font face="monospace">|<code>|g' \
                 -e 's|</font>|</code>|g')
  sprintly issue update --id "$id" --description "$body"
done
```

Two things worth knowing before you run this over 50 issues:

- `issue update` replaces the description wholesale, so always start from the value `--field` just handed you — never from a value you reconstructed by hand.
- Dry-run first: drop the `issue update` line and `diff` the transformed body against the original to confirm the substitution does what you think.

## 13. Pull single values out for scripting

```bash
# One scalar, straight into a shell variable
status=$(sprintly issue show 244 --field status --json | jq -r .name)

# A custom field by id (`Commit` flag, CF 69)
sprintly issue show 244 --field cf:69 --raw

# All comments of an issue as JSON, newest text only
sprintly issue show 244 --comments --json | jq -r '.comments[].text'

# Ids of the sub-tasks that are not done yet
sprintly issue list --parent 161 --status open --all --json \
  | jq -r '.[] | "\(.id)\t\(.status.name)\t\(.subject)"'
```

Prefer this over `--columns`: a table cell is squeezed onto one line, so any multi-line value (descriptions, HTML-bearing custom fields) is fine to *look* at but not to *use*.

## 14. Attach files to an issue

The only supported way to get a file into the tracker. Several `--file`
arguments produce **one** journal entry, so a comment plus three files is a
single history record rather than four.

```bash
# One file with a comment
sprintly attachment upload --id 257 --file ./leads.csv \
  --notes "<p>Final list, 66 rows.</p>"

# Several files, still one journal entry
sprintly attachment upload --id 257 --file ./leads.csv --file ./brief.md

# Store under a different name (single --file only)
sprintly attachment upload --id 257 --file ./tmp.html --filename "report Q3.html"
```

The command prints the new attachment IDs; feed one straight back to verify the
round trip:

```bash
ID=$(sprintly attachment upload --id 257 --file ./leads.csv --json \
      | python3 -c "import json,sys;print(json.load(sys.stdin)['uploaded'][0]['id'])")
sprintly attachment download --id "$ID" -o ./roundtrip.csv
diff ./leads.csv ./roundtrip.csv && echo "byte-identical"
```

Filenames with spaces or non-ASCII characters are fine — the stored name is
reused verbatim for the download, which is exactly why the two REST steps must
not be done by hand.

## 15. Call the REST API for something the CLI does not cover

`sprintly token` refreshes the session and prints a valid access token, one line
and nothing else, so it composes directly into `curl`.

```bash
BASE=https://db.sprintly.cloud

# Delete a stale attachment (no CLI subcommand for this)
curl -s -X DELETE -H "Authorization: Bearer $(sprintly token)" \
  "$BASE/api/attachments/101.json"
```

Do **not** read `accessToken` out of `config.json` by hand. Tokens live about
five minutes, so a hand-read value is frequently expired already, and the
resulting `401` arrives as an HTML body — which surfaces as a JSON parse error
in the caller rather than an authentication error, and costs an hour to debug.

For a long run, call `sprintly token` per request rather than caching it once at
the top of the script.
